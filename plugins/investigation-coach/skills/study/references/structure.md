# Study material structure

Load only when writing. **Frontmatter first, marker second** — Obsidian only parses a frontmatter
block that starts at byte 0, so a marker line above it costs the note its tags:

```markdown
---
tags: [study, <area>]
---
> Generated by /investigation-coach:study · YYYY-MM-DD
```

The marker therefore lands within the first 10 lines, which is where the overwrite check looks.
The vault root is `docs/`, so a wikilink that leaves this directory is vault-absolute from there —
`[[onboarding/architecture]]` — never `../`, which Obsidian does not resolve.

## index.md

1. **Threshold concepts** — the 2-3 ideas that make everything else in this codebase click
   (e.g. "everything is an eval", "hooks may warn but never block"). Each in 2-4 sentences with
   the one file to read. This section is the whole payoff of the index: a reader who gets these
   can navigate the rest alone.
2. **Reading order** — a numbered path through the study files, shortest useful sequence first.
3. **What lives where** — one line per study file, wikilinked.
4. **Discovered areas** — name the areas this project's architecture yielded and, when a reader
   might expect one that isn't there, say why ("no UI area — this project ships no frontend"),
   so absence reads as a fact, not an omission.

## Discovering the areas

Never assume a layout — read the structure and name what is actually there. Signals, in order:
`docs/onboarding/stack.md` roots if `/onboard` ran · workspace/monorepo manifests · top-level
directories that own a runtime (a package.json here, a service Dockerfile there) · the deploy
units. Typical outcomes: `backend/ frontend/` for a classic web app · one directory per service
for microservices · `engine/ cli/` for a tool · `api/ workers/ web/` for a queue-backed app.
Area names are the project's own vocabulary (what the team calls them), sanitized for filenames.
`cross-cutting/` is always present; no other directory is scaffolded on spec.

## Area files (one directory per discovered area, + cross-cutting/)

One file per concern, named for the pattern or technology (`repository-pattern.md`,
`event-driven-jobs.md`, `error-handling.md`). Fixed shape:

```markdown
## What it is here        <- one paragraph: the pattern AS THIS CODEBASE uses it, not the textbook
## Why here               <- the problem it solves in this project; what the alternative would cost
## Where to see it        <- the proving instance: file:line, plus 1-2 more sites
## What it trades away    <- the honest cost: what this choice makes harder
## How it interacts       <- wikilinks: [[other-pattern]], [[onboarding/<note>]],
                             [[onboarding/components/<name>]] for the component that shows it
## Read next              <- one wikilink, the natural next file in the reading order
```

## Voice rules

- Diátaxis **explanation**: understanding-oriented, discursive, connects decisions to reasons.
  Never imperative steps ("run X, then Y" is onboarding's job), never parameter tables
  (reference's job).
- The textbook definition of a pattern gets at most one sentence; the rest is this codebase's
  version of it — including where the codebase deviates from the textbook, which is usually the
  most instructive part.
- cross-cutting/ covers what every feature touches: auth, error handling, configuration,
  logging/observability, testing strategy. These are the files that save a newcomer from
  re-deriving house rules by trial and error.
- Cite migrations as patterns too: "moved off X, don't add new X" is a design decision a reader
  must study, and git history is its evidence.
