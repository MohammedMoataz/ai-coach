# Output formats

Load only when writing. Every generated file carries
`> Generated by /investigation-coach:<skill> · YYYY-MM-DD`, where `<skill>` names whichever skill
wrote it — `onboard` or `map`, which share `features/`; `components/` belongs to `map` alone, and
`onboard` links those notes without ever writing one. The
`/investigation-coach:` prefix is the overwrite permission: absent means hand-written, and
hand-written files are never regenerated silently, by any skill.

**Frontmatter comes first, the marker second.** Obsidian only parses a frontmatter block that
starts at byte 0 — a marker line above it silently costs you every tag and alias in the file. So a
note with frontmatter opens with its `---` block and puts the marker on the line after it; a note
without frontmatter keeps the marker on line 1. Either way it lands within the first 10 lines,
which is where the overwrite check looks:

```markdown
---
tags: [onboarding, <area>]
aliases: [<class or service name if it differs from the title>]
---
> Generated by /investigation-coach:onboard · YYYY-MM-DD
```

Tags come from a fixed vocabulary so the graph view can colour by them: `onboarding` on everything
here, plus `component` on a component note, `feature` on a feature note, and the discovered area
name. Frontmatter carries nothing else — Obsidian reads `tags` and `aliases`, and a key it ignores
is a key that rots.

All notes are Obsidian-ready. The vault root is `docs/`, so wikilinks that cross a directory are
vault-absolute from there — `[[onboarding/components/api-gateway]]`,
`[[business/processes/checkout]]` — and never use `../`, which Obsidian does not resolve. A link
inside one directory can stay bare: `[[start-here]]`. Every note keeps at least one outbound link
so nothing orphans the graph.

## index.md — the hub (MOC pattern)

Links only, one line of context each — never a bare list. A section appears only when its target
exists; the last two are what stops `/investigation-coach:map`'s output orphaning:

```markdown
## Start
- [[start-here]] — setup, first task, and the vocabulary you'll hear in standup
## Reference
- [[stack]] — where things live and what commands to run
- [[decisions]] — why it's built this way (inferred, marked as such)
## Patterns
- [[01-<topic>]] — <one line: when you'll hit this>
## Features
- [[onboarding/features/<name>]] — <one line: what it does for whom>
## The shape of it
- [[onboarding/architecture]] — components and what talks to what
- [[onboarding/components/<name>]] — <one line: what it is responsible for>
```

A link that stays in this directory is bare (`[[start-here]]`); one that leaves it names the path
from the vault root, `docs/`. When no component notes exist yet, the last section is the single
`[[onboarding/architecture]]` line and one sentence pointing at `/investigation-coach:map` for the
rest; when `map` has not run either, the section is omitted rather than left linking nothing.

## start-here.md — sections, in order

1. **Setup → first run** — exact commands, from clone to the thing working locally.
2. **Your first task** — one suggested small, real task (a good first issue shape), with the
   files it touches. Scoped for an early win, not mastery.
3. **Core flows** — the 2-4 flows that define the product, each a short trace with `file:line`
   per hop.
4. **Glossary** — the team/domain words a newcomer hears and won't find defined anywhere else.
5. **How we work** — review, deploy, and code norms, mined from CLAUDE.md / CONTRIBUTING / lint
   configs and cited to them.
6. **Who to ask** — from `.ai-coach/team.md` when present (names, roles); otherwise omit the
   section rather than invent it.
7. **Companion step** — one line pointing at the sibling skills: `/investigation-coach:map` for the
   architecture picture, `/investigation-coach:study` for why the patterns are what they are. This
   doc covers what the project *is*; those cover its shape and its reasoning.

## stack.md — lookup table, no prose

Roots are one line per **discovered architectural area** — the project's real shape (backend/
frontend, one root per service, engine/cli — whatever is actually there), never a preset pair:

```markdown
roots:
- <area>: <path>            (one line per discovered area, in the project's own vocabulary)
build_cmd: <cmd>            test_cmd: <cmd> (single file: <cmd>)
lint_cmd: <cmd>             docs_dir: <path>
conventions:
- <auth / validation / state / API style / DB / module system / runtime version — one line each>
- migrated OFF <X> → <Y> (<evidence>) — do not add new <X>
```

## decisions.md — inferred ADRs

3-5 entries, Nygard shape, each headed `### D<n> — <choice> (INFERRED)`:
`**Context**` (what problem the code visibly had) · `**Decision**` (what was chosen, evidence) ·
`**Consequences**` (what a newcomer must respect because of it). INFERRED is honest labelling:
these are reverse-engineered from the code, not minutes from a meeting.

## patterns/NN-<topic>.md — fixed skeleton

```markdown
## Quick reference    <- the 5-second version: when this applies, what to copy
## Pattern template   <- minimal skeleton code lifted from a real instance
## CRITICAL rules     <- imperative, negative-first: "NEVER throw from callApi — return { error }"
## DO / DON'T         <- the mistakes the codebase's own history shows people make
Reference: <file>:<lines>, <file>:<lines>   <- citation list, one line, always present
```

## features/<name>.md — the eight-section feature format

Title + generated-by line, then: **Overview** · **Domain model** (table: Entity | Type | Key
properties | Relationships | Source) · **API surface** (split Commands / Queries) · **one
section per discovered area the feature touches** (the project's own areas — UI, worker, CLI,
service — or "none — <why>") · **End-to-end flow** (one operation traced entry point → handler →
domain → side effects, a `file:line` per hop) · **Permissions** · **Dependencies** · **Related**
(wikilinks).

**Related** is where a feature note joins the graph, so it is never empty: one
`[[onboarding/components/<name>]]` per component the flow touches, plus the process note
(`[[business/processes/<name>]]`) and the spec (`[[features/<slug>/spec]]`) when strategy-coach has
written them. Frontmatter `tags: [onboarding, feature]`.
