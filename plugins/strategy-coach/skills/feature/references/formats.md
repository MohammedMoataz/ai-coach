# spec.md and plan.md

Load when writing. Both files live in `docs/features/<slug>/` and both start with:

```
> Generated by /strategy-coach:feature · YYYY-MM-DD
```

Two files, deliberately. `spec.md` is the review and sign-off unit. `plan.md` must stand alone,
because the session that executes it may be handed nothing else. The DoD table appears in both —
duplicated on purpose, regenerated together, never edited in one place only.

## spec.md

```markdown
> Generated by /strategy-coach:feature · YYYY-MM-DD
---
tags: [feature, spec]
---

# <Feature name>

**Goal:** <the outcome that changes, for whom — one sentence, in the user's words>
**Requested by:** <who> · <date>
**Business context:** [[../../business/processes/<process>]] — the process this changes

## Why now

<Two or three sentences. What is happening today that makes this worth building. If the answer is
"a customer asked", say which and what they were trying to finish.>

## Scope

**In:**
- <capability, stated as something a user can do afterwards>

**Out — deliberately:**
- <the thing a reasonable reader would assume is included, and is not>

The "out" list is not padding. It is the difference between a review that approves and a review
that discovers a misunderstanding.

## Rejected approaches

| Approach | Why not |
|---|---|
| <what was considered> | <the reason, from the user or from prior art> |

Omit this section only when nothing was rejected. Usually something was.

## Definition of done

Every row is pass or fail with no argument. `Check` is a command, a test name, or `observable:`
plus where to see it.

| # | Criterion | Check | Evidence expected |
|---|---|---|---|
| 1 | Partial refunds above the settled amount are rejected | `npm test -- refunds/validate` | new test passes, names the boundary case |
| 2 | Rejection reason reaches the operator | `observable: refund UI shows "exceeds settled amount"` | screenshot or the rendered string |
| 3 | No change to auto-approval for wallet payments | `npm test -- refunds/approval` | existing suite still green |

Not criteria: "performance is acceptable", "the code is clean", "it works end to end". If it
cannot be checked, it belongs in Unknowns.

## Unknowns

- <what is unresolved, and who can resolve it>

Required. A spec with no unknowns is claiming certainty that a first draft never has.
```

## plan.md

Written **only after sign-off**. Its reader is a fresh session on a cheap model with no memory of
the conversation that produced it — so it resolves every ambiguity in advance, states criteria
rather than steps, names files by path with something to imitate, and says what comes back. That is
the `/prompt-coach:dispatch` contract; this file is an instance of it.

```markdown
> Generated by /strategy-coach:feature · YYYY-MM-DD
---
tags: [feature, plan]
---

# Plan — <Feature name>

**Read first:** `docs/features/<slug>/spec.md`. This file repeats what you need; the spec has the
reasoning.

## Task

<Two to four sentences. What to build, stated so that someone who has never seen this repo could
start. No "as discussed", no "that file", no pronoun without a referent.>

## Context you need

| Thing | Where |
|---|---|
| The process this changes | `docs/business/processes/<process>.md` |
| The code that owns it | `@src/refunds/validate.ts` |
| A file to imitate | `@src/payments/validate.ts` — same shape, same test layout |
| Project conventions | `docs/onboarding/stack.md` |

## Done when

<The DoD table from spec.md, verbatim. Same rows, same checks.>

## Out of scope

- <one line each — the same list as the spec's "Out">

## What to return

Findings first. Every claim names `file:line` or the command you ran. If a criterion could not be
met, say which and why — do not silently narrow the scope. End with one line on what you could not
determine.

## Unknowns carried into execution

- <the spec's unknowns that the executor will hit, and what to do when they do — usually: stop and
  report, do not guess>

## Changelog

- YYYY-MM-DD — first version
```

## The `--amend` flow

1. Read both files. A file missing the marker line is hand-owned — do not rewrite it; use it as
   input and say so in the report.
2. Regenerate what you own, appending a `## Changelog` line naming the date and what changed.
3. Re-run the sign-off gate. An amended DoD that nobody re-approved is the same failure as a plan
   written without approval.
4. Never leave the two files describing different criteria.
